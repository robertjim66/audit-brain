# 审计智脑 业务说明书

> 面向新同事与非审计背景的读者。不需要技术背景，读完能明白这套系统解决什么问题、自己该在哪一环参与。
>
> 文中所有数字门槛均取自系统实际运行的判定规则，非估算值。

---

## 一、这套系统解决什么问题

### 1.1 现状：审计员在做什么

建设工程结算审计，本质是回答一个问题：**施工单位报的钱，有没有多报？**

要回答这个问题，审计人员得把一个项目的东西凑齐了看：

- **工程量清单**——中标时约定的单价是多少（"约定价"）
- **结算书**——施工单位最终报了多少（"结算价"）
- **合同**——约定了什么条款、怎么结算
- **签证单**——施工过程中有没有发生额外的事、要不要额外给钱
- **发票、付款凭证**——钱到底付没付、付了多少
- **竣工资料**——工程实际做没做成这样

一个不算小的项目，结算书就动辄几百页，签证单几十份。全靠人一份一份翻、一页一页对。

### 1.2 人工做这件事的三个问题

| 问题 | 具体表现 |
| --- | --- |
| **慢** | 大量时间花在翻找和誊抄上，真正用于判断的时间被压缩 |
| **漏** | 眼睛会疲劳。一份 50 页的结算书，某个单价差 2 元，很可能就看漏了；签证单少一个章，更不容易发现 |
| **说不清责任** | 结论记在谁名下？改了没有？谁改的？事后说不清 |

### 1.3 系统的定位

一句话：**AI 负责"翻找"和"比对"，人负责"判断"。**

具体分工：

| 谁 | 干什么 |
| --- | --- |
| 系统 | 把资料读成可比对的数据、两边一比找差异、按经验规则扫出可疑点、记录谁处理的 |
| 审计人员 | 判断差异是否合理、决定这条疑点算不算问题、下结论、出报告 |

**必须明确的边界**：系统**不产出审计结论**。它只回答"哪里可能有问题、证据在哪里"，最终结论由人下。

## 二、一条完整的业务主线

整个流程六步。每一步的产出，都是下一步的输入。

```
1. 建项目  →  2. 传资料  →  3. AI 识读  →  4. 跑核对  →  5. 沉淀疑点  →  6. 出报告
   ↓            ↓             ↓            ↓            ↓            ↓
一个项目     原始资料      可比对的内容    差异清单    待核查清单   结论材料
空间
```

### 步骤 1：建项目

确定审计对象，并标注项目类型：造价/结算审计、工程审计、竣工决算。

一个项目就是一个独立的空间，所有资料、核对结果、疑点都归属到它下面。项目有"进行中"和"已完成"两个状态。

### 步骤 2：传资料

把项目涉及的资料传进来，并**标注业务类别**——这一步很关键：

| 类别 | 典型资料 | 为什么必须标 |
| --- | --- | --- |
| 清单 | 工程量清单（Excel） | 勾稽的"左方" |
| 结算 | 结算审核书 | 勾稽的"右方" |
| 控制价 | 招标控制价 | 勾稽的"右方" |
| 合同 | 施工合同、协议 | 签章核对 |
| 签证 | 变更单、洽商单、联系单 | 签章核对 + 要素检查 |
| 发票 | 增值税发票 | 连号检查 |
| 照片 | 现场照片 | — |
| 支付 | 付款凭证 | — |

系统按这个标注决定"拿哪份资料做什么"，标错会导致核对结果不对。系统也会根据文件名自动猜类别，但**建议人工确认**。

### 步骤 3：AI 识读

上传的图片和 PDF 会被识别成可检索、可比对的内容：

- **Excel / Word**：直接解析出表格与文字
- **PDF / 图片**：走 OCR 识别（需要配置识别服务密钥）

识别完成后，页面上能看到原文与识别出的表格。**这一步不需要人工录入**，是系统替人做的活。

### 步骤 4：跑核对

执行勾稽程序，自动比对两边数据。产出**差异清单**——哪些项目两边不一样、差多少。

### 步骤 5：沉淀疑点

差异结果自动转成疑点，同时按经验规则再扫一遍。产出**待核查清单**——这是审计人员真正要逐条处理的东西。

### 步骤 6：出报告

导出 Excel 核对台账（内部工作底稿）或 Word 疑点发现清单（对外报告）。

## 三、核对程序：它在核什么

### 3.1 先讲透核心概念："左方 vs 右方"

建设工程审计的核心动作，是拿两样东西对在一起看：

| | 左方 | 右方 |
| --- | --- | --- |
| 是什么 | 中标时的**约定价** | 结算时的**申报价** |
| 常见来源 | 工程量清单 | 结算书 / 招标控制价 |

**为什么要比**：施工单位按清单报价，结算时只能按实际做了多少算。正常情况下两边应该对得上。对不上，要么是多报了，要么是漏报了，要么是有正当理由的变更。

### 3.2 贯穿全文的例子

假设清单里有这样一个子目：

> 办公桌　单价 20 元/个　数量 10 个

结算书上报：

> 办公桌　单价 18 元/个　数量 10 个

人来看：单价降了 2 元，数量没变，合价少了 20 元。

**系统做的事，就是把这种"两边一比就知道"的情况全部找出来。** 一个项目几千个子目，人工比对要几天，系统几分钟跑完——但这只是"找出来"，合不合理还要人判断。

### 3.3 程序一：清单 ↔ 结算跨页表勾稽

**比什么**：工程量、综合单价、合价，三项逐项比。

| 比对项 | 看什么 | 差异意味着 |
| --- | --- | --- |
| 工程量 | 清单数量 vs 结算数量 | 可能多算/少算了实物量 |
| 综合单价 | 清单单价 vs 结算单价 | 可能改了单价 |
| 合价 | 清单合价 vs 结算合价 | 最终金额差异 |

**怎么配对**：靠**清单项目编码**（9 到 13 位数字），不靠名称。

> 为什么不靠名称？因为名称会写错——同一个东西，施工单位可能叫"办公桌"、"办公台"、"钢制办公桌"。编码是唯一的，配对不会串。

**三种结论，含义各不相同**：

| 结论 | 什么时候出现 | 业务含义 |
| --- | --- | --- |
| **一致** | 三项比对都在容差内 | 这项两边对得上，不用管 |
| **差异** | 至少一项超出容差 | **需要人工判断**：是合理变更还是多报？ |
| **无法确认** | 某一边没数据，或数值都没识别出来 | **不等于没问题**，而是核不了 |

**"无法确认"这个结论很重要**，单独说明：

系统不会在资料不全时瞎猜。如果只传了结算书没传清单，或者某个子目的金额根本没识别出来，系统会明确记为"无法确认"，并说明**缺什么**。

它的业务意义是：**防止把"没核到"当成"没问题"**。这比给出一个错误的"一致"要安全得多。

差异之外，系统还会汇总两件事：

- **核增金额** — 结算比清单多报了多少
- **核减金额** — 结算比清单少报了多少

这是审计报告里的核心数字。

### 3.4 程序二：签证 / 合同三方签章证据链核对

**背景知识**：一份有效的工程签证单，需要**三方**共同签字盖章：

| 方 | 通常叫什么 |
| --- | --- |
| 建设单位 | 发包人、甲方 |
| 监理单位 | 监理人、总监理工程师 |
| 施工单位 | 承包人、乙方、中标单位 |

三方齐全，签证才具备作为结算依据的效力。少一方，就可能只是施工方单方面要求。

**查两种异常**：

| 异常 | 描述 | 风险 | 业务含义 |
| --- | --- | --- | --- |
| **有栏无章** | 文档里有该方的签字位置，但整页没识别到任何印章 | 高 | 写了要签字，实际没签 |
| **未见该方** | 全文都找不到该方的签字栏 | 中 | 三方会签缺一方 |

**业务价值**：签字盖章齐全与否，直接决定这份签证**能不能作为结算依据**。缺章的签证单若被计入结算金额，问题就大了。

如果所有资料里一处印章都没识别到，系统会单独记一条，提示可能是"全部未盖章"或"识别失败需人工核实"。

## 四、疑点台账：它在找什么

疑点有两个来源：

1. **核对差异自动汇入** — 上一章的差异结果直接转成疑点，省去二次录入
2. **规则扫描** — 按工程审计积累的经验，扫出人工容易漏掉的模式

两者最终汇入同一本台账，统一管理。

### 4.1 六类规则，逐条看

#### 1. 量差异常

**在警惕什么**：结算多算或少算了工程量、单价。

**怎么发现**：来自清单↔结算核对。系统把两边对不上的子目全部转成疑点，并算出差额。

**风险分级**：按差额金额——**≥10 万为高风险，≥1 万为中风险，其余为低风险**。

#### 2. 签章异常

**在警惕什么**：签证单要素不全、该盖章的没盖、三方缺签。

**怎么发现**：两条线。一是签章核对程序发现的"有栏无章""未见该方"；二是逐份检查签证单是否有**编号、日期、签章**三个基本要素。

**风险分级**：要素**缺 3 项为高风险**（高风险意味着完全不可用），**缺 2 项为中风险**，缺 1 项为低风险。

> 为什么要素齐全重要？因为要素不全的签证单，真实性本身就存疑，不宜单独作为结算依据。

#### 3. 凑整金额

**在警惕什么**：整千、整万的金额可能是估算出来的，而不是算出来的。实际工程量很少正好是整数。

**触发门槛**：金额 **≥2000 元且是整千数**（如 3,000、10,000、25,000）。

**为什么盯这个**：一个子目报 10,000 元，看起来是"算出来的"，但也可能是把不确定的部分凑成了整千。凑整会掩盖真实的工程量或单价差异。

**风险分级**：≥5 万且为整万数为中风险，其余为低风险。

#### 4. 连号发票

**在警惕什么**：同一批开出来的发票被拆开报销，或同一笔业务开了多张发票。

**触发门槛**：同一发票代码下，发票号码**连号 ≥2 张**即记录。

**为什么盯这个**：税务系统批量开票时号码是连着的。如果一批连号发票都报到了同一个项目，很可能是一笔业务拆成了多笔，或者存在重复报销。

**风险分级**：一律为**高风险**。

#### 5. 集中签证

**在警惕什么**：竣工之后集中补办签证。

**触发门槛**：**30 天内出现 ≥2 份签证**；**≥3 份为高风险**，2 份为中风险。

**为什么盯这个**：正常情况下，现场发生变更应当**及时**办理签证。如果一大把签证集中在竣工前后，很可能是工程快结束时才集中补的单子——此时人已经离场，现场情况难以核实，签证金额的真实性也就难以验证。

**怎么进一步查**：调取竣工验收报告与监理日志，比对签证日期与竣工时间的先后。

#### 6. 资料缺口

**在警惕什么**：资料本身不完整，导致某些项核不了。

**怎么发现**：跑核对时，如果一侧提取不到任何可比对数据，系统会记一条资料缺口疑点，说明"因缺这一侧，N 条明细只能记为无法确认"。

**业务意义**：这一条提醒的是**审计覆盖度不足**——不是发现了问题，而是**该查的没能查**。审计报告里需要说明范围和限制，这类记录就是依据。

### 4.2 风险分级怎么定的

系统按金额分档为主，特殊类型按规则本身定级：

| 风险 | 判断依据 |
| --- | --- |
| **高风险** | 差额 ≥10 万；或签章要素缺 3 项；有栏无章；连号发票；30 天内 ≥3 份签证 |
| **中风险** | 差额 ≥1 万；或签章要素缺 2 项；凑整 ≥5 万整万；30 天内 2 份签证 |
| **低风险** | 差额 <1 万；或仅缺 1 项要素；小额凑整 |

**分级的意义是排序，不是定性**。低风险不等于没问题，只是更可能是正常业务波动。高风险也仍需人判断，只是建议优先处理。

## 五、疑点怎么处置（责任怎么落地）

### 5.1 四个状态

| 状态 | 含义 |
| --- | --- |
| **待处理** | 系统刚发现，还没人看 |
| **已确认** | 人工核实，这**确实是个问题**，需要跟进整改 |
| **误报** | 人工核实，系统**判错了**，予以排除 |
| **已关闭** | 处理完成，归档 |

从"待处理"点进任一状态，就是在**为这条疑点负责**。

### 5.2 处理人留痕

每次改动状态，系统自动记录四件事：

- **谁**改的
- **什么时候**改的
- **从什么状态改成了什么**
- 当时填的**处置备注**

这些记录累积成一条完整的**处置历史**，可以随时回看。比如：

```
张三   2026-03-05  将状态从「待处理」改为「已确认」   备注：已与施工单位核对，属实
李四   2026-03-12  将状态从「已确认」改为「误报」     备注：该项属合理组价调整
```

**业务价值**：责任可追溯。三个月后被问"这条疑点当时谁定的、依据是什么"，能答得上来。

### 5.3 已处置的疑点不能删除

这是有意加的限制，业务理由是：**已确认或已判误报的疑点，都属于审计结论记录**。删掉等于销毁工作底稿。

如果确实需要删除（比如确认是系统误识别、这条压根不该存在），必须先把它改回"待处理"再删。

### 5.4 处置状态与对外输出的关系

| 产出物 | 用途 | 是否含处理人 |
| --- | --- | --- |
| Excel 核对台账 | **内部**工作底稿 | ✅ 含处理人与处置时间 |
| Word 疑点发现清单 | **对外**报告 | ❌ 不含 |

对外报告不暴露内部责任分工，这是常规做法。

## 六、角色与协作

一个审计项目通常不止一个人参与。系统分两种角色：

| 角色 | 可以做 | 不可以做 |
| --- | --- | --- |
| **归属人**（owner） | 建项目、编辑项目、管理成员、删除项目、跑核对、处置疑点 | — |
| **复核人**（reviewer） | 传资料、跑核对、处置疑点、查看 | ❌ 不能编辑/删除项目，不能增删成员 |

**怎么加成员**：项目详情页 → 成员管理 → 添加。只有归属人能操作。

**为什么要分角色**：核心是**责任可追溯**。一个项目多人参与时，每条结论都知道是谁定的。同时也防止误操作——比如复核人不小心把整个项目删了。

## 七、当前尚未实现的部分

如实列出，避免按文档去找不存在的东西。

### 7.1 核对程序：规划 4 个，实现了 2 个

| 程序 | 状态 |
| --- | --- |
| 清单 ↔ 结算跨页表勾稽 | ✅ 已实现 |
| 签证 / 合同三方签章证据链核对 | ✅ 已实现 |
| **合同付款核对**（付款金额 vs 合同约定 vs 结算） | ❌ 尚未开发 |
| **汇总勾稽**（各专业分册与总汇总的交叉核对） | ❌ 尚未开发 |

### 7.2 疑点规则：规划 8 类，实现了 6 类

已实现：量差异常、签章异常、凑整金额、连号发票、集中签证、资料缺口。

尚未开发：

- **重复计量** — 同一个工程内容在不同部位/子目里重复报量。这是工程结算审计的核心疑点类型之一，目前没有自动规则覆盖。
- **缺少影像资料** — 缺少能证明工程实际发生或现场情况的照片凭证。

### 7.3 其他限制

| 限制 | 说明 |
| --- | --- |
| 疑点台账不能手工录入 | 目前疑点只能由系统生成。如果审计过程中发现系统没覆盖的问题，暂时无法手工登记 |
| 核对差异明细不分页 | 差异项较多时页面较长 |
| 资料数量上限 | 单项目最多 500 份资料 |
| 图像坐标框线未渲染 | AI 已识别出图中文字的位置，但页面上还没画出来 |
| 图片识别需外部服务 | PDF 与图片的 OCR 依赖外部识别服务，未配置时无法识读 |

## 八、最终产出什么

### 8.1 Excel 核对台账（内部工作底稿）

包含四张表：

| 表 | 内容 |
| --- | --- |
| **汇总** | 各核对程序的执行情况、差异总数、核增/核减金额 |
| **清单勾稽明细** | 逐个子目的左右两侧数据、差异金额、核对结论 |
| **签章核对** | 逐页逐方的签章情况与核对结论 |
| **疑点台账** | 全部疑点，含类型、风险、描述、建议、金额、证据位置、状态、**处理人**、**处置时间** |

### 8.2 Word 疑点发现清单（对外报告）

表格包含：类型、风险、疑点描述、审计建议、金额、证据位置。

不含处理人与处置时间——对外报告不体现内部责任分工。
